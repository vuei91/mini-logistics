# 면접 예상 질문 & 답변 — CJ Logistics Mini

물류 화주-차주 매칭·배차 프로젝트 기반. 실제 구현에 근거한 답변과 예상 꼬리질문을 정리했습니다.

> 답변은 **상황 → 문제 → 해결 → 결과/근거** 흐름으로 말하는 것을 권장합니다.

---

## 1. RabbitMQ 이벤트 처리 & Outbox 패턴 (핵심 강점)

### Q. RabbitMQ로 이벤트를 발행할 때 왜 바로 발행하지 않고 Outbox 패턴을 썼나요?

**핵심 답변**
배차 확정·운송 완료 같은 비즈니스 처리와 이벤트 발행을 동시에 성공시켜야 하는데, DB 트랜잭션과 메시지 브로커는 서로 다른 시스템이라 **이중 쓰기(dual write) 불일치** 위험이 있습니다. "DB는 커밋됐는데 RabbitMQ 발행은 실패"하면 이벤트가 유실되고, 반대로 "발행은 됐는데 DB가 롤백"되면 유령 이벤트가 나갑니다.

그래서 발행을 트랜잭션 밖으로 미루고, **같은 트랜잭션 안에서 이벤트를 `outbox_events` 테이블에 PENDING으로 저장**했습니다. 비즈니스 데이터와 이벤트가 하나의 원자적 커밋으로 묶이니, 커밋이 성공하면 이벤트는 반드시 남습니다. 이후 별도 스케줄러(`OutboxEventRelay`)가 PENDING을 폴링해 RabbitMQ에 발행하고 PUBLISHED로 전이합니다.

**근거 코드**: `DispatchService.accept()` / `updateShipmentStatus(COMPLETED)`에서 `outboxEventStore.store(...)`, `OutboxEventRelay.publishPendingEvents()`(@Scheduled).

#### 꼬리질문 대비
- **Q. 릴레이가 발행 후 PUBLISHED 전이 직전에 죽으면?**
  → 재기동 시 여전히 PENDING이라 재발행됩니다. 즉 **at-least-once** 전달이고, 중복 가능성이 있어 컨슈머는 멱등(idempotent)하게 설계해야 합니다. (이벤트에 고유 ID를 두고 처리 여부를 확인하는 방식)
- **Q. 폴링 방식의 단점은? 대안은?**
  → 폴링은 지연(기본 1초)과 불필요한 조회가 있습니다. 대안으로 CDC(Debezium 등)로 outbox 테이블 변경을 캡처해 발행하면 지연을 줄일 수 있습니다. 이 프로젝트 규모에선 스케줄러 폴링이 단순하고 충분하다고 판단했습니다.
- **Q. 순서 보장은?**
  → 릴레이가 `created_at` 오름차순으로 조회해 발행합니다. 다만 다중 인스턴스로 릴레이가 병렬 실행되면 순서가 흔들릴 수 있어, 현재는 단일 릴레이 전제입니다.

### Q. 메시지 소비가 실패하면 어떻게 되나요?

**핵심 답변**
Topic Exchange에 연결된 큐에 **DLX(Dead Letter Exchange)/DLQ**를 설정했습니다. 컨슈머가 재시도(최대 3회)를 소진하고도 실패하면 메시지를 requeue하지 않고 DLQ로 보내 격리합니다. 정상 트래픽을 막지 않으면서 실패 메시지를 따로 조사·재처리할 수 있습니다.

**근거 코드**: `RabbitMqConfig`의 `x-dead-letter-exchange` 설정, DLQ 바인딩. `RabbitMqMessagingIntegrationTest`에서 반복 실패 시 DLQ 이동을 검증.

#### 꼬리질문 대비
- **Q. 이걸 어떻게 검증했나요?**
  → **Testcontainers로 실제 RabbitMQ 컨테이너를 띄워** 통합 테스트했습니다. 정상 발행→소비, Outbox의 PENDING→PUBLISHED 전이, 그리고 강제 실패 메시지가 재시도 소진 후 DLQ로 이동하는 것까지 Awaitility로 비동기 검증했습니다. 목(mock)이 아니라 실제 브로커로 검증한 점이 신뢰도를 높입니다.

## 2. 배차 동시성 제어

### Q. 한 기사가 동시에 여러 배차에 잡히는 문제는 어떻게 막았나요?

**핵심 답변**
두 요청이 거의 동시에 같은 기사를 배차하려는 경쟁 상태가 생길 수 있습니다. 이를 막기 위해 배차 확정 시점에 기사 레코드를 **비관적 락(`SELECT ... FOR UPDATE`)** 으로 조회하고(`findByIdForUpdate`), 락을 잡은 상태에서 그 기사에게 진행 중인 배차(`PROPOSED`/`ACCEPTED`)가 있는지 재검증합니다. 이미 있으면 `DriverAlreadyAssignedException`을 던져 중복 배차를 차단합니다.

**근거 코드**: `DispatchService.matchAndDispatch()` — `driverRepository.findByIdForUpdate(...)` + `existsByDriverIdAndStatusIn(...)`.

#### 꼬리질문 대비
- **Q. 왜 낙관적 락이 아니라 비관적 락인가요?**
  → 배차는 충돌 시 재시도 비용보다 "확실히 한 명만 잡는 것"이 중요하고, 짧은 트랜잭션이라 락 보유 시간이 길지 않습니다. 낙관적 락은 충돌 시 예외 후 재시도 로직이 필요한데, 배차는 재시도해도 이미 다른 요청이 잡았을 가능성이 높아 비관적 락이 의도에 더 맞다고 판단했습니다.
- **Q. 분산 환경(다중 인스턴스)에서도 유효한가요?**
  → 네. `FOR UPDATE`는 DB 레벨 락이라 애플리케이션 인스턴스가 여러 개여도 동일 레코드에 대한 직렬화가 보장됩니다. 단, 락 경합이 심해지면 처리량이 떨어질 수 있어, 대규모에선 파티셔닝이나 큐 기반 순차 처리를 고려할 수 있습니다.
- **Q. 데드락 가능성은?**
  → 단일 기사 레코드만 잠그고 트랜잭션이 짧아 순환 대기 가능성은 낮습니다. 여러 리소스를 잠근다면 잠금 순서를 일관되게 정하는 규칙이 필요합니다.

## 3. 도메인 설계 (상태 머신 & 전략 패턴)

### Q. 상태 전이 로직을 어디에 뒀고, 왜 그렇게 했나요?

**핵심 답변**
상태 전이를 서비스가 아니라 **엔티티 메서드에 캡슐화**했습니다. 예를 들어 `ShipmentRequest.startMatching()`은 현재 상태가 REQUESTED일 때만 MATCHING으로 바꾸고, 아니면 예외를 던집니다. 상태 규칙이 도메인 객체 안에 응집되어, 어느 서비스에서 호출하든 불법 전이가 원천 차단됩니다(리치 도메인 모델). 서비스가 상태를 직접 세팅하면 규칙이 여러 곳에 흩어져 일관성이 깨지기 쉽습니다.

**근거 코드**: `ShipmentRequest`의 `startMatching/confirmDispatch/complete` 등, `Dispatch`의 `accept/reject/markCompleted`.

### Q. 매칭 알고리즘은 어떻게 설계했나요?

**핵심 답변**
`MatchingStrategy` 인터페이스로 매칭 로직을 분리했습니다. 기본 구현은 가용 기사 중 **차량 종류 일치 + 적재중량 충족**으로 필터링한 뒤, 기본 100점에 **선호 노선이 일치하면 30점을 가산**해 점수 내림차순으로 후보를 반환합니다. 전략 패턴이라 나중에 거리·평점 기반 등 다른 알고리즘으로 교체하거나 A/B 테스트하기 쉽습니다.

**근거 코드**: `DefaultMatchingStrategy.findCandidates()`.

#### 꼬리질문 대비
- **Q. 실제 거리를 안 쓰고 점수를 매기는데 한계는?**
  → 맞습니다. 현재는 지역 문자열 일치와 선호노선만 봅니다. 실서비스라면 지오코딩·경로 API로 실거리/ETA를 반영해야 하고, 운임 계산도 그에 맞춰 정교화해야 합니다. 인터페이스를 분리해둔 이유가 이런 고도화를 코드 변경 최소화로 흡수하기 위함입니다.

## 4. 인증/인가

### Q. 인증은 어떻게 구현했나요?

**핵심 답변**
무상태(STATELESS) JWT 방식입니다. 로그인 시 email(subject), role, profileId를 클레임에 담아 HMAC-SHA로 서명한 토큰을 발급하고, `JwtAuthenticationFilter`가 `Authorization: Bearer` 헤더를 파싱해 `ROLE_{role}` 권한을 SecurityContext에 세팅합니다. 세션을 두지 않아 수평 확장에 유리합니다.

### Q. 권한 체크는 어떻게 하나요?

**핵심 답변**
**이중 방어**로 설계했습니다. 1차로 `SecurityConfig`에서 URL·HTTP 메서드별 역할 접근제어(화물요청은 SHIPPER, 배차는 DRIVER)를 하고, 2차로 서비스 계층에서 **리소스 소유권을 검증**합니다(`verifyShipperOwnership`/`verifyDriverOwnership`). 같은 SHIPPER라도 남의 화물요청은 조회·취소할 수 없습니다. URL 규칙만으로는 "역할은 맞지만 남의 리소스" 케이스를 막지 못하기 때문입니다.

#### 꼬리질문 대비
- **Q. SSE 알림 스트림은 헤더 인증을 어떻게 했나요?**
  → 브라우저 `EventSource`가 커스텀 헤더를 못 보내는 제약이 있어, 스트림 엔드포인트만 예외적으로 JWT를 **쿼리 파라미터**로 받아 검증했습니다. 트레이드오프로 URL에 토큰이 노출될 수 있어, 실서비스라면 단기 토큰이나 WebSocket 서브프로토콜 인증을 고려할 것입니다.
- **Q. 토큰 만료/갱신은?**
  → 현재 만료(기본 1시간)만 두고 리프레시 토큰은 없습니다. 실서비스라면 리프레시 토큰 + 블랙리스트(로그아웃) 전략을 추가할 지점입니다.

## 5. 클라우드 배포 & 트러블슈팅

### Q. 배포 아키텍처를 설명해주세요.

**핵심 답변**
프론트는 S3+CloudFront 정적 호스팅, API는 EC2의 Docker Compose(Spring Boot + RabbitMQ), DB는 RDS PostgreSQL입니다. 핵심은 **CloudFront 단일 도메인**으로 프론트와 API를 통합한 것입니다. `/api/*`는 EC2 오리진으로, 나머지는 S3로 라우팅합니다. 이렇게 하면 프론트와 API가 같은 오리진이라 CORS·Mixed Content 문제가 사라지고, TLS는 CloudFront 엣지에서 종단 처리해 백엔드를 HTTPS로 만들 필요가 없습니다.

### Q. 배포하면서 겪은 가장 까다로운 문제는?

**핵심 답변 (STAR)**
정적 export한 SPA에서 화물요청 상세 페이지(`/shipper/requests/2`)가 `AccessDenied`가 났습니다. 원인은 Next.js 정적 export가 **빌드 시점에 아는 경로만 HTML로 생성**하는데, 동적 세그먼트 `[id]`의 실제 id 파일이 S3에 없어서였습니다.

처음엔 CloudFront Function으로 placeholder 페이지에 rewrite했는데, 이번엔 클라이언트 라우터가 파라미터를 `placeholder`로 읽어 "잘못된 요청" 오류가 났습니다. 즉 **정적 export와 동적 세그먼트의 궁합 문제**가 근본 원인이었습니다.

그래서 우회 대신 **동적 라우트를 쿼리스트링(`?id=`) 방식으로 재설계**했습니다. 그러면 페이지는 정적 파일 하나로 충분하고, 클라이언트가 `useSearchParams`로 id를 읽어 URL과 라우터가 항상 일치합니다. 결과적으로 CloudFront 특수 규칙도 제거해 구성이 단순해졌습니다.

**교훈**: 문제를 인프라 우회로 덮기보다 원인(정적 호스팅 제약)을 규명하고 앱 설계를 바꾸는 편이 장기적으로 단순하고 견고했습니다.

#### 꼬리질문 대비
- **Q. CloudFront가 EC2에 접근을 못 해 504가 났다던데?**
  → 8080 보안그룹이 특정 IP만 허용하고 있어서였습니다. CloudFront 엣지는 IP가 유동적이라, AWS **관리형 prefix list**(cloudfront origin-facing)를 소스로 지정해 CloudFront에서 오는 트래픽만 허용하도록 좁혔습니다.
- **Q. API 응답이 HTML로 왔다는 건?**
  → CloudFront 커스텀 에러 응답(403/404→index.html)이 배포 전역에 적용돼서, 백엔드가 낸 정상적인 404/403 API 응답까지 index.html(HTML 200)로 바꿔버린 문제였습니다. 커스텀 에러 응답을 제거하고, `/api/*`는 건드리지 않는 CloudFront Function으로 SPA 폴백을 대체해 해결했습니다.

### Q. 왜 EC2에서 빌드하지 않고 ECR 이미지를 쓰나요?

**핵심 답변**
초기엔 EC2에서 `git pull` 후 `docker compose --build`로 직접 빌드했는데, EC2 리소스로 매번 빌드하니 느리고 부하가 컸습니다. 이미지를 로컬/CI에서 빌드해 **ECR에 push하고 EC2는 pull만** 하도록 바꿔, 배포 시간과 EC2 부하를 줄이고 "빌드된 산출물을 그대로 배포"하는 일관성을 확보했습니다.

## 6. 테스트 전략

### Q. 테스트는 어떤 계층으로 구성했나요?

**핵심 답변**
- **단위**: 서비스(Mockito), 엔티티 상태 머신, 매칭 전략, JWT 서비스
- **컨트롤러 슬라이스**: `@WebMvcTest`로 요청/응답·검증·보안 매핑
- **통합**: 시큐리티(역할/소유권), 목록 조회, OpenAPI 스모크
- **메시징 통합**: Testcontainers로 실제 RabbitMQ 검증

총 80여 개입니다. 특히 메시징처럼 **인프라와 강하게 결합된 부분은 목이 아니라 실제 컨테이너로 검증**해야 신뢰할 수 있다고 봤습니다.

#### 꼬리질문 대비
- **Q. 테스트에서 겪은 이슈는?**
  → Docker Engine 29+가 요구하는 API 버전과 Testcontainers의 docker-java 클라이언트 기본 협상 버전이 안 맞아 실패한 적이 있어, `api.version`을 1.44로 고정해 해결했습니다. (build.gradle에 기록)

## 7. 자주 나오는 일반 질문 대비

- **Q. 이 프로젝트에서 가장 어필하고 싶은 한 가지는?**
  → Outbox 패턴 + RabbitMQ + DLQ를 **Testcontainers로 실제 검증**한 이벤트 파이프라인입니다. 물류 배차처럼 이벤트 유실이 곧 서비스 신뢰도 문제인 도메인에서 핵심 역량이라고 생각합니다.
- **Q. 아쉬운 점 / 개선하고 싶은 것은?**
  → 컨슈머 멱등성 보강, 리프레시 토큰, 실거리 기반 매칭·운임, 관측성(로깅/메트릭/트레이싱), K8s 이전을 우선순위로 두고 있습니다.
- **Q. 혼자 만든 프로젝트인데 협업은?**
  → 커밋 단위를 기능별로 나누고, `.gitignore`로 시크릿을 분리하고, 문서(구현/포트폴리오)를 남겨 온보딩 비용을 낮추는 습관을 들였습니다.
